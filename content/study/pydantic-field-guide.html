Chapter 1 · Foundations

What is Pydantic?

Pydanticnoun · Python data validation library

A library that turns Python type hints into runtime rules. You describe the shape of your data as a class with typed fields; Pydantic checks incoming data against it, converts it to the right types where it safely can, and raises one clear error listing every problem when it cannot.

Python type hints are normally ignored at runtime: def f(x: int) happily accepts "hello". Pydantic reads those hints and enforces them. Its core is written in Rust (pydantic-core), so validation is fast enough to run on every request of a busy API.

The problem Pydantic solves

Every program reads data it did not create: JSON from an HTTP request, rows from a CSV, environment variables, the output of an LLM. That data is untrusted. Without a validation layer you write the same defensive code again and again:

without Pydantic
def create_user(payload: dict):
    if "id" not in payload:
        raise ValueError("id missing")
    try:
        user_id = int(payload["id"])
    except (TypeError, ValueError):
        raise ValueError("id must be an integer")
    name = payload.get("name")
    if not isinstance(name, str) or not name.strip():
        raise ValueError("name must be a non-empty string")
    # ... 30 more lines for email, dates, nested addresses ...
with Pydantic
from pydantic import BaseModel, Field

class User(BaseModel):
    id: int
    name: str = Field(min_length=1)

user = User.model_validate(payload)   # validated, converted, typed

Easy definition

A model is a class that describes the shape of valid data. Validation turns raw input into an instance of that class or raises an error. Serialization turns the instance back into dicts or JSON.

Chapter 3 · Foundations

How validation works

When Python defines your class, Pydantic reads the annotations and builds a core schema: a tree describing every field, type, constraint and validator. pydantic-core compiles that schema into a Rust validator and serializer, stored on the class. Each call to model_validate walks the input once through that compiled validator.

Example

Lax mode vs strict mode

By default Pydantic runs in lax mode: it accepts input that can be converted without losing information. "42" becomes 42, but 4.5 is rejected for an int because the fraction would be lost. Strict mode accepts only the exact type.

strict.py
from pydantic import BaseModel, ConfigDict, Field, StrictInt

class Strict(BaseModel):
    model_config = ConfigDict(strict=True)   # whole model strict
    n: int

class Mixed(BaseModel):
    a: StrictInt                     # this field only
    b: int = Field(strict=True)      # same thing via Field
    c: int                           # lax

Strict(n="5")                                 # fails
Strict.model_validate({"n": "5"}, strict=False)  # per-call override: passes
1 validation error for Strict n Input should be a valid integer [type=int_type, input_value='5', input_type=str]
Strict from JSON

JSON has no date, UUID or Decimal types, so strict mode still accepts their string forms when you call model_validate_json. Strict mode stops surprising conversions, not impossible ones.

When to choose strict

Keep lax for HTTP, CSV, form data and env vars: those always arrive as strings. Use strict for internal Python-to-Python calls, financial values, and anywhere a silent "1" to True conversion would hide a bug.

Fields, types and defaults

A field is a class attribute with a type annotation. Whether it is required depends only on whether it has a default, never on whether its type allows None. This is the single most misunderstood rule in Pydantic.

Required vs optional: every combination

Example

Five fields, five behaviours

required_matrix.py

from pydantic import BaseModel, Field

class M(BaseModel):

Mutable defaults are safe

In plain Python, def f(x=[]) shares one list between calls. Pydantic deep-copies mutable defaults per instance, so tags: list[str] = [] is fine:

python
class Mut(BaseModel):
    tags: list[str] = []

a, b = Mut(), Mut()
a.tags.append("x")
print(a.tags, b.tags)
['x'] []

Field() and constraints

A type says what kind of value. A constraint says which values of that kind are allowed. Constraints are declared with Field(...) and are checked in Rust, so they are faster than writing a validator.

Example

A product with four constraints, all violated

Reusable constrained types with Annotated

Put the type and its constraints in one alias and reuse it everywhere. This is the idiomatic v2 style; the v1 helpers conint/constr still work but are discouraged.

types.py
from typing import Annotated
from pydantic import Field, StringConstraints

Username   = Annotated[str, StringConstraints(strip_whitespace=True, to_lower=True,
                                              min_length=3, max_length=20,
                                              pattern=r"^[a-z0-9_]+$")]
Percentage = Annotated[float, Field(ge=0, le=100)]
Quantity   = Annotated[int, Field(ge=1, le=999)]

class Order(BaseModel):
    buyer: Username
    discount: Percentage = 0
    lines: list[Quantity] = Field(min_length=1)   # list of 1..999, at least one

Ready-made aliases exist too: PositiveInt, NonNegativeInt, PositiveFloat, NegativeInt, FiniteFloat, StrictStr, StrictBool, FutureDate, PastDatetime, AwareDatetime.

Chapter 6 · Models and validation

Nested models, unions and enums

Nesting

A field typed as another model validates a nested dict into that model. Errors report the full path (loc) to the bad value.

nested.py
class Address(BaseModel):
    city: str
    pin: str = Field(pattern=r"^\d{6}$")

class Customer(BaseModel):
    name: str
    addresses: list[Address]

Customer.model_validate({
    "name": "Asha",
    "addresses": [{"city": "Pune", "pin": "411001"}, {"city": "Delhi", "pin": "11"}],
})
# error loc: addresses.1.pin  -> second address, pin field

Unions and smart mode

int | str tries each member. In the default smart mode Pydantic first looks for an exact type match across all members, then falls back to lax conversion. So "1" stays a string for int | str, while 1 stays an int. Use Field(union_mode="left_to_right") if you want the first member that succeeds to win.

Discriminated unions

When union members are models, add a tag field with a Literal type and name it as the discriminator. Pydantic reads the tag and validates against exactly one model: faster, and the error tells you which branch failed instead of listing every member's failures.

Example

Pets keyed by pet_type

discriminated.py
from typing import Annotated, Literal, Union
from pydantic import BaseModel, Field

class Cat(BaseModel):
    pet_type: Literal["cat"]
    meows: int

class Dog(BaseModel):
    pet_type: Literal["dog"]
    barks: float

class Owner(BaseModel):
    pet: Annotated[Union[Cat, Dog], Field(discriminator="pet_type")]

Owner(pet={"pet_type": "dog", "barks": 3})     # Dog
Owner(pet={"pet_type": "fish"})                # unknown tag
Owner(pet={"pet_type": "dog", "barks": "x"})   # right branch, bad field
Owner(pet=Dog(pet_type='dog', barks=3.0)) 1 validation error for Owner pet Input tag 'fish' found using 'pet_type' does not match any of the expected tags: 'cat', 'dog' [type=union_tag_invalid, ...] 1 validation error for Owner pet.dog.barks Input should be a valid number, unable to parse string as a number [type=float_parsing, ...]
Use this for LLM output and events

Discriminated unions are the right shape for "the model may return one of several actions" ({"action": "search", ...} vs {"action": "answer", ...}) and for webhook or event payloads.

Enums and Literal

python
from enum import Enum

class Status(str, Enum):     # str mixin: serializes as plain strings
    open = "open"
    closed = "closed"

class Ticket(BaseModel):
    status: Status = Status.open
    priority: Literal["low", "medium", "high"] = "medium"

Ticket(status="closed").status        # Status.closed
Ticket(priority="urgent")             # Input should be 'low', 'medium' or 'high'

Prefer Literal for small, local sets of strings; prefer Enum when the values are used across the codebase and you want named constants.

Chapter 7 · Models and validation

Validators

When types and constraints cannot express a rule, write a validator: a function Pydantic calls during validation. Return the (possibly changed) value to accept it; raise ValueError or AssertionError to reject it. Pydantic wraps your exception into a ValidationError with the right loc.

The four modes

ModeRunsReceivesUse for
after (default)after Pydantic's own type checkan already-typed valueBusiness rules: "must be even", "end after start". Safest choice.
beforebefore the type checkraw input (anything)Normalising input: split "a,b" into a list, strip text
wraparound the type checkraw input + a handler to callTry validation, recover from a specific failure
plaininstead of the type checkraw inputFull control; Pydantic's own check is skipped
Example

Field validator plus a cross-field model validator

signup.py
from pydantic import BaseModel, field_validator, model_validator

class Signup(BaseModel):
    email: str
    password: str
    confirm: str

    @field_validator("email")            # mode="after" by default
    @classmethod
    def normalise_email(cls, v: str) -> str:
        if "@" not in v:
            raise ValueError("must contain @")
        return v.strip().lower()

    @model_validator(mode="after")       # whole object, all fields valid
    def passwords_match(self):
        if self.password != self.confirm:
            raise ValueError("passwords do not match")
        return self

Signup(email="  Asha@X.COM ", password="p", confirm="p")
Signup(email="nope", password="p", confirm="p")
Signup(email="a@b.c", password="p", confirm="q")
Signup(email='asha@x.com', password='p', confirm='p') 1 validation error for Signup email Value error, must contain @ [type=value_error, input_value='nope', input_type=str] 1 validation error for Signup Value error, passwords do not match [type=value_error, input_value={'email': 'a@b.c', ...}, input_type=dict]

The model-level error has an empty loc because it belongs to the whole object. (In real code, store passwords as SecretStr: see Chapter 16.)

Before, wrap and Annotated validators

modes.py
from typing import Annotated, Any
from pydantic import (BaseModel, Field, field_validator, model_validator,
                      AfterValidator, BeforeValidator, ValidationError,
                      ValidatorFunctionWrapHandler)

# 1. before: accept "a, b, c" as well as a real list
class Post(BaseModel):
    tags: list[str]

    @field_validator("tags", mode="before")
    @classmethod
    def split_csv(cls, v: Any) -> Any:
        if isinstance(v, str):
            return [t.strip() for t in v.split(",") if t.strip()]
        return v                      # let Pydantic validate everything else

# 2. wrap: truncate instead of failing on too-long input
class Code(BaseModel):
    code: Annotated[str, Field(max_length=5)]

    @field_validator("code", mode="wrap")
    @classmethod
    def truncate(cls, v: Any, handler: ValidatorFunctionWrapHandler) -> str:
        try:
            return handler(v)                         # normal validation
        except ValidationError as err:
            if err.errors()[0]["type"] == "string_too_long":
                return handler(v[:5])
            raise

print(Code(code="ABCDEFGH"))        # code='ABCDE'

# 3. reusable validators via Annotated (no decorator, no class needed)
def must_be_even(v: int) -> int:
    if v % 2:
        raise ValueError("must be even")
    return v

Even     = Annotated[int, AfterValidator(must_be_even)]
Stripped = Annotated[str, BeforeValidator(lambda v: v.strip() if isinstance(v, str) else v)]

# 4. model before: accept a compact string form of the whole object
class Pair(BaseModel):
    key: str
    value: int

    @model_validator(mode="before")
    @classmethod
    def from_string(cls, data: Any) -> Any:
        if isinstance(data, str):            # "x=5"
            k, v = data.split("=")
            return {"key": k, "value": v}
        return data

Pair.model_validate("x=5")          # Pair(key='x', value=5)

Order of execution

  1. Model before validators run on the raw input dict.
  2. For each field, in definition order: before and wrap validators, last-declared first; then the core type check and constraints; then after validators, first-declared first. A @field_validator counts as declared after any Annotated validators on that field.
  3. Model after validators run on the built instance. They only run if every field passed.
Validators see earlier fields only

In a field validator, info.data holds fields defined above the current one that already passed. For rules that involve several fields, use a model_validator(mode="after") instead of reaching into info.data.

Validation context

Pass runtime information (the current user, a list of banned words, a tenant id) into validators without global variables:

context.py
from pydantic import ValidationInfo
from pydantic_core import PydanticCustomError

class Comment(BaseModel):
    word: str

    @field_validator("word")
    @classmethod
    def not_banned(cls, v: str, info: ValidationInfo) -> str:
        banned = (info.context or {}).get("banned", set())
        if v in banned:
            raise PydanticCustomError("banned_word", "'{word}' is not allowed", {"word": v})
        return v

Comment.model_validate({"word": "spam"}, context={"banned": {"spam"}})

Turning errors into a friendly API response

def to_problems(e: ValidationError) -> list[dict]:
    return [
        {"field": ".".join(str(p) for p in err["loc"]) or "(body)",
         "code": err["type"],
         "message": err["msg"]}
        for err in e.errors(include_input=False, include_url=False)
    ]

try:
    Invoice.model_validate_json('{"vendor":"Acme","total":"twelve","currency":"GBP"}')
except ValidationError as e:
    for p in to_problems(e):
        print(p["field"], "->", p["message"])

Custom error types

ValueError always becomes type=value_error. Raise PydanticCustomError(type, message_template, ctx) when clients need a stable code of their own, as in the banned_word example in Chapter 7.

Chapter 9 · Data out and config

Serialization

Serialization is validation in reverse: turning a model into a dict or JSON. Two methods do almost everything:

  • model_dump() returns a Python dict. By default values keep their Python types (datetime, UUID, Decimal, enum members).
  • model_dump_json() returns a JSON str, produced in Rust. Faster than json.dumps(m.model_dump()) and it knows how to encode dates, UUIDs and Decimals.

model_dump(mode="json") gives a dict containing only JSON-safe values: use it when another library will call json.dumps on the result.

Example

python mode vs json mode, plus a custom field serializer

dump_modes.py
from datetime import datetime

Chapter 16 · Beyond BaseModel

SecretStr and handling secrets

SecretStrtype · pydantic.SecretStr

A string wrapper that hides its value everywhere it would normally be shown: repr(), str(), f-strings, logs, tracebacks, model_dump() and model_dump_json(). You read the real value only by calling .get_secret_value(). SecretBytes does the same for bytes, and Secret[T] for any type.

Passwords, API keys, tokens, database URLs with credentials and webhook signing keys all end up in model objects. Those objects get printed in debug sessions, written to logs by error handlers, sent to Sentry, and dumped into JSON responses. A plain str leaks in all of those places. SecretStr makes "show it" an explicit, searchable act.

Example

What a SecretStr shows, and what it keeps

secret_basics.py
from pydantic import BaseModel, Field, SecretBytes, SecretStr

class Login(BaseModel):
    username: str
    password: SecretStr = Field(min_length=8)
    token: SecretBytes | None = None

l = Login(username="asha", password="hunter2!!", token=b"abc")

print(repr(l))
print(f"pw={l.password}")
print(l.model_dump())
print(l.model_dump_json())
print(l.password.get_secret_value(), l.token.get_secret_value())   # explicit reveal
print(len(l.password), l.password == SecretStr("hunter2!!"), l.password == "hunter2!!")
Login(username='asha', password=SecretStr('**********'), token=SecretBytes(b'**********')) pw=********** {'username': 'asha', 'password': SecretStr('**********'), 'token': SecretBytes(b'**********')} {"username":"asha","password":"**********","token":"**********"} hunter2!! b'abc' 9 True False

The mask is always ten stars regardless of length, so it reveals nothing. len() works (handy for checks) and two SecretStr objects compare by value, but a SecretStr never equals a plain str.

Constraints and validation on secrets

Length constraints work directly. Note the different error type: too_short, not string_too_short. pattern does not work on SecretStr and raises a TypeError at validation time. Use Secret[...] around a constrained str, or an AfterValidator:

secret_rules.py
import re
from typing import Annotated
from pydantic import AfterValidator, BaseModel, ConfigDict, Field, Secret, SecretStr, StringConstraints

# ✗ TypeError: Unable to apply constraint 'pattern' to supplied value **********
# pin: Annotated[SecretStr, StringConstraints(pattern=r"^\d{4}$")]

# ✓ option 1: wrap a constrained str in Secret[...]
Pin = Secret[Annotated[str, StringConstraints(pattern=r"^\d{4}$")]]

# ✓ option 2: validate the revealed value in an after validator
def strong(v: SecretStr) -> SecretStr:
    s = v.get_secret_value()
    if not (re.search(r"\d", s) and re.search(r"[A-Z]", s)):
        raise ValueError("password needs a digit and an uppercase letter")
    return v                      # return the SecretStr, not s

class Register(BaseModel):
    model_config = ConfigDict(hide_input_in_errors=True)
    pin: Pin
    password: Annotated[SecretStr, Field(min_length=8), AfterValidator(strong)]

Secret[T] works for non-string values too: Secret[date] for a date of birth, Secret[int] for a PIN number. .get_secret_value() returns the validated date or int.

Three traps (all verified on 2.14)

Trap 1 · The raw secret appears in ValidationError

A failed secret field prints input_value='short': the actual password. Error messages end up in logs. Set ConfigDict(hide_input_in_errors=True) on models that hold secrets. That cleans the message, but e.errors() still contains 'input': 'short', so when you return errors to a client (FastAPI 422 bodies include input) call e.errors(include_input=False).

trap1.py
class Login(BaseModel):
    model_config = ConfigDict(hide_input_in_errors=True)
    password: SecretStr = Field(min_length=8)

try:
    Login(password="short")
except ValidationError as e:
    print(e)                                        # no input_value in the text
    print(e.errors()[0]["input"])                   # 'short'  still here!
    print(e.errors(include_input=False))            # safe to return to a client
1 validation error for Login password Value should have at least 8 items after validation, not 5 [type=too_short] short [{'type': 'too_short', 'loc': ('password',), 'msg': 'Value should have at least 8 items after validation, not 5', 'ctx': {...}}]
Trap 2 · JSON round trip destroys the secret

model_dump_json() writes "**********". Validating that JSON back gives a SecretStr whose real value is the ten stars. Caching a settings object to disk or a queue this way silently corrupts it. If you truly must serialize the value (for example, to an encrypted store), add a serializer that reveals it, and only for that purpose:

trap2.py
dumped = Login(password="hunter2!!").model_dump_json()
Login.model_validate_json(dumped).password.get_secret_value()   # '**********'  data lost

class StoredCredential(BaseModel):
    api_key: SecretStr

    @field_serializer("api_key", when_used="json")
    def reveal(self, v: SecretStr) -> str:
        return v.get_secret_value()      # JSON shows the key; dict and repr stay masked

StoredCredential(api_key="sk-live-123").model_dump_json()   # '{"api_key":"sk-live-123"}'
Trap 3 · It is a mask, not encryption

SecretStr is a wrapper, not a security boundary (it even accepts a plain str in strict mode). Anything that can reach the object can call .get_secret_value(), and once you assign the revealed value to a variable or put it in an f-string, the protection is gone. Reveal inline at the call site; never log, return or cache the revealed value.

Where values come from (highest priority first)

  1. Arguments passed to the constructor: Settings(debug=True)
  2. Environment variables (names are case-insensitive by default)
  3. The .env file(s) in env_file
  4. Secret files in secrets_dir (Docker/Kubernetes secrets: one file per value)
  5. Field defaults
Habits that pay off

Every credential is a SecretStr. Keep .env out of git and commit a .env.example. Provide settings through a cached function (FastAPI: Depends(get_settings)) so tests can override them. Use cli_parse_args=True to get a typed CLI for free.

Chapter 19 · Implementation

Pydantic in FastAPI

FastAPI is built on Pydantic. A parameter typed as a model is read from the JSON body and validated; a failure becomes an automatic 422 response listing the .errors(). The response_model filters and serializes what you return. Your FastAPI Field Guide covers the HTTP side; this chapter covers the model design.

Separate input, output and update models

Never use one model for everything. Inputs must not let clients set id or created_at; outputs must never contain passwords; updates must make every field optional.

Example

The Create / Update / Out pattern

schemas.py + main.py
from datetime import datetime, timezone
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel, ConfigDict, EmailStr, Field, SecretStr

class StrictBase(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True,
                              hide_input_in_errors=True)

class UserBase(StrictBase):
    email: EmailStr
    full_name: str = Field(min_length=1, max_length=80)

class UserCreate(UserBase):                    # POST body
    password: SecretStr = Field(min_length=8)

class UserUpdate(StrictBase):                  # PATCH body: everything optional
    email: EmailStr | None = None
    full_name: str | None = Field(default=None, min_length=1, max_length=80)

class UserOut(UserBase):                       # response: no password
    model_config = ConfigDict(from_attributes=True)   # build from ORM rows
    id: int
    created_at: datetime

app = FastAPI()
DB: dict[int, dict] = {}

@app.post("/users", response_model=UserOut, status_code=status.HTTP_201_CREATED)
def create_user(body: UserCreate):
    uid = len(DB) + 1
    row = body.model_dump(exclude={"password"}) | {
        "id": uid,
        "created_at": datetime.now(timezone.utc),
        "password_hash": hash_password(body.password.get_secret_value()),
    }
    DB[uid] = row
    return row          # response_model drops password_hash automatically

@app.patch("/users/{uid}", response_model=UserOut)
def update_user(uid: int, body: UserUpdate):
    if uid not in DB:
        raise HTTPException(404, "user not found")
    DB[uid] |= body.model_dump(exclude_unset=True)   # only fields the client sent
    return DB[uid]
PATCH needs exclude_unset

Without exclude_unset=True, a PATCH that sends only {"full_name": "B"} would also write email=None and wipe the stored email.

422 bodies echo the input

FastAPI's default 422 response includes each error's input, including a rejected password. For endpoints that accept secrets, register a RequestValidationError handler that returns exc.errors() with the input key removed (see the capstone).

Pydantic for LLM apps

LLMs produce text. Applications need typed data. Pydantic is the bridge in both directions: model_json_schema() tells the model what to produce, and model_validate_json() checks that it did.

What the API enforces vs what Pydantic enforces

Structured outputs support types, enum/Literal, anyOf, $ref and string formats like date and email. They do not support minimum/maximum, minLength/maxLength or recursive schemas. The Python SDK removes unsupported constraints from the schema it sends and checks them client-side. Cross-field rules (totals add up, end after start) live only in your validators, so always keep a validation step you own.

Two layers. InvoiceDraft is what the LLM fills: simple types only, so it fits the structured-output schema rules. Invoice is the domain model with Decimal money and the rules that matter to the business.

models.py
from datetime import date
from decimal import Decimal
from typing import Annotated, Literal
from pydantic import (BaseModel, ConfigDict, Field, computed_field,
                      field_validator, model_validator)

Currency = Literal["INR", "USD", "EUR", "GBP"]

# ---------- layer 1: what the LLM produces ----------
class LineDraft(BaseModel):
    description: str
    quantity: float
    unit_price: str = Field(description="Unit price as a plain decimal string, no symbols, e.g. '1250.00'")

class InvoiceDraft(BaseModel):
    """Data extracted from one invoice. Use null when a value is not in the text; never guess."""
    invoice_number: str | None
    vendor: str
    issue_date: str | None = Field(description="YYYY-MM-DD")
    due_date: str | None = Field(description="YYYY-MM-DD")
    currency: Currency
    lines: list[LineDraft]
    stated_total: str = Field(description="Grand total printed on the invoice, plain decimal string")

# ---------- layer 2: the business model ----------
Money = Annotated[Decimal, Field(max_digits=14, decimal_places=2, ge=0)]

class Line(BaseModel):
    model_config = ConfigDict(frozen=True)
    description: str = Field(min_length=1)
    quantity: Decimal = Field(gt=0)
    unit_price: Money

    @computed_field
    @property
    def amount(self) -> Decimal:
        return (self.quantity * self.unit_price).quantize(Decimal("0.01"))

class Invoice(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    invoice_number: str | None = None
    vendor: str = Field(min_length=2)
    issue_date: date | None = None
    due_date: date | None = None
    currency: Currency
    lines: list[Line] = Field(min_length=1)
    stated_total: Money

    @field_validator("vendor")
    @classmethod
    def tidy_vendor(cls, v: str) -> str:
        return " ".join(v.split())

    @computed_field
    @property
    def computed_total(self) -> Decimal:
        return sum((l.amount for l in self.lines), Decimal("0.00"))

    @model_validator(mode="after")
    def check_rules(self):
        if self.issue_date and self.due_date and self.due_date < self.issue_date:
            raise ValueError("due_date is before issue_date")
        if abs(self.computed_total - self.stated_total) > Decimal("0.05"):
            raise ValueError(f"line items add up to {self.computed_total}, "
                             f"but the stated total is {self.stated_total}")
        return self

# ---------- API models ----------
class ExtractRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    text: str = Field(min_length=20, description="Raw invoice text")

class Problem(BaseModel):
    field: str
    code: str
    message: str

class ExtractOk(BaseModel):
    status: Literal["ok"] = "ok"
    attempts: int
    invoice: Invoice

    status: Literal["failed"] = "failed"
    attempts: int

3. extractor.py

extractor.py
import anthropic
from pydantic import ValidationError
from models import ExtractFailed, ExtractOk, Invoice, InvoiceDraft, Problem
from settings import Settings

SYSTEM = ("You extract invoices into the given schema. Copy numbers exactly as printed. "
          "Use null for anything the text does not state.")

def to_problems(e: ValidationError) -> list[Problem]:
    return [Problem(field=".".join(map(str, err["loc"])) or "(invoice)",
                    code=err["type"], message=err["msg"])
            for err in e.errors(include_input=False, include_url=False)]

class Extractor:
    def __init__(self, settings: Settings):
        self.settings = settings
        self.client = anthropic.Anthropic(
            api_key=settings.anthropic_api_key.get_secret_value())   # revealed only here

    def run(self, text: str) -> ExtractOk | ExtractFailed:
        messages = [{"role": "user", "content": f"Invoice text:\n\n{text}"}]
        problems: list[Problem] = []
        attempts = 0
        for attempts in range(1, self.settings.max_retries + 2):
            response = self.client.messages.parse(
                model=self.settings.model,
                max_tokens=16000,
                system=SYSTEM,
                messages=messages,
                output_format=InvoiceDraft,
            )
            if response.stop_reason in ("refusal", "max_tokens") or response.parsed_output is None:
                problems = [Problem(field="(llm)", code=str(response.stop_reason),
                                    message="model returned no usable output")]
                break
            draft: InvoiceDraft = response.parsed_output
            try:
                invoice = Invoice.model_validate(draft.model_dump())
                return ExtractOk(attempts=attempts, invoice=invoice)
            except ValidationError as e:
                problems = to_problems(e)
                feedback = "\n".join(f"- {p.field}: {p.message}" for p in problems)
                messages += [
                    {"role": "assistant", "content": draft.model_dump_json()},
                    {"role": "user", "content":
                        f"That extraction failed these checks:\n{feedback}\n"
                        "Re-read the invoice and correct only what is wrong."},
                ]
        return ExtractFailed(attempts=attempts, problems=problems)

Best practices

Boundaries

Validate once at every edge (HTTP, files, env, LLM output, queues) · trust typed objects inside · model_validate_json for raw JSON.

Model design

Separate Create / Update / Out models · shared StrictBase with extra="forbid" · reusable Annotated types · Literal and discriminated unions over free strings.

Validation

Constraints before validators · after mode by default · cross-field rules in model_validator(mode="after") · branch on error type, never msg.

Secrets

Every credential is SecretStr · hide_input_in_errors=True · errors(include_input=False) in responses · reveal inline at the point of use.

Data out

response_model / Out models control exposure · exclude_unset for PATCH · mode="json" when another library serializes.

Performance

Module-level TypeAdapters · validate lists in one call · Rust constraints over Python validators · defer_build for big codebases.

Glossary

AliasExternal name for a field used when reading and/or writing data.
Annotatedtyping.Annotated[T, ...]: a type plus metadata (constraints, validators, serializers).
BaseModelThe base class for Pydantic models.
BaseSettingsModel that loads values from env vars and files (pydantic-settings).
CoercionConverting input to the field type, e.g. "42" to 42.
Computed fieldA property included in dumps and the schema.
ConfigDictModel-wide settings in model_config.
ConstraintA rule on a value (gt, max_length, pattern) checked in Rust.
Core schemaInternal tree that pydantic-core compiles into a validator and serializer.
Discriminated unionUnion of models chosen by a tag field.
FieldA typed attribute of a model; Field() adds defaults, constraints and metadata.
JSON SchemaStandard JSON description of data shape; generated by model_json_schema().
Lax modeDefault mode: safe conversions allowed.
pydantic-coreThe Rust engine that does validation and serialization.
Private attribute_name attribute: not validated, dumped or in the schema.
RootModelModel whose top level is a single value such as a list.
Secret / SecretStr / SecretBytesWrappers that mask a value in repr, logs and dumps until .get_secret_value().
SerializationTurning a model into a dict or JSON.
Strict modeOnly the exact type is accepted.
TypeAdapterValidation and serialization for any type, not just models.
ValidationErrorException listing every validation failure with type, loc, msg and input.
ValidatorYour function run during validation (before, after, wrap, plain; field or model level).
