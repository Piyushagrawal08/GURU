Chapter 1 · Foundations

What is Docker?

Dockernoun · open-source container platform

A platform for packaging an application together with everything it needs to run (runtime, libraries, system tools, config) into a single unit called an image, and then running that image as an isolated process called a container. The same image runs the same way on your laptop, a teammate's laptop, a CI server and a cloud VM.

Docker did not invent containers (Linux had chroot, cgroups and namespaces for years), but in 2013 it made them easy: one file to describe the environment (Dockerfile), one command to build it, one command to run it, and a public registry (Docker Hub) to share it. The image format was later standardised by the Open Container Initiative (OCI), so images you build with Docker also run on Podman, Kubernetes, AWS ECS, Google Cloud Run and others.

The problem Docker solves

Before containers, deploying meant writing long setup instructions: "install Python 3.12, then these system libraries, then set these variables…". Every machine drifted a little. The result was the classic bug report: "It works on my machine."

  • Environment drift. Dev has Python 3.12 and OpenSSL 3; the server has Python 3.9. Code that ran locally crashes in production.
  • Dependency conflicts. App A needs numpy 1.x, app B needs numpy 2.x on the same server.
  • Slow onboarding. A new developer spends a day installing Postgres, Redis and the right Node version.
  • Heavy isolation. The old fix was one virtual machine per app: slow to boot, gigabytes each.
Example

"Works on my machine" vs "ships the machine"

Without Docker you ship only code and hope the target matches. With Docker you ship an image that already contains the exact runtime and libraries.

The shipping-container analogy

Before standard shipping containers, every cargo (barrels, sacks, cars) was loaded by hand in a different way. The steel container standardised the box, so ships, cranes and trucks no longer cared what was inside. Docker does the same for software: the host, CI and cloud only need to know how to run "a container"; they do not care if it holds Python, Java, Node or a database.

Where Docker fits (and where it does not)

Great for

Web APIs and microservices · reproducible dev environments · running databases locally · CI pipelines · packaging ML models and LLM servers · shipping CLI tools · trying software without installing it.

Not the right tool for

Desktop GUI apps · running a different OS kernel (a Windows app inside a Linux container) · hard real-time workloads · as a security boundary for fully untrusted code on its own (use VMs or gVisor/Kata for that).

Easy definition

An image is a recipe-built, read-only snapshot of an app and its environment. A container is a running instance of that image. Docker is the tool that builds images and runs containers.

Chapter 2 · Foundations

Containers vs virtual machines

Both give isolation, but at different layers. A virtual machine emulates hardware and runs a full guest operating system with its own kernel. A container is just a normal process on the host, fenced off by kernel features, sharing the host's kernel.

How Docker runs on Windows and macOS

Linux containers need a Linux kernel. Docker Desktop on Windows runs a tiny Linux VM via WSL 2; on macOS it uses Apple's Virtualization framework. You do not see the VM: the docker command in PowerShell talks to it transparently. This is also why bind-mounted files on Windows are faster when the project lives inside the WSL filesystem (\\wsl$\Ubuntu\home\…).

Containers and VMs are not rivals in practice. In the cloud, your containers usually run inside VMs (an EC2 instance, an Azure VM, a Kubernetes node).

Docker architecture

Docker uses a client–server design. The docker command you type is only a client. It sends REST API calls to the Docker daemon (dockerd), which does the real work: building images, running containers, managing networks and volumes. The daemon pulls and pushes images to a registry.

Chapter 6 · Images and containers

Running containers

docker run is the command you will type most. It pulls the image if needed, creates a container, and starts it. Its flags decide how the container connects to the outside world.

terminal
# 1. A web server in the background, port 8080 on your machine -> 80 in the container
docker run -d --name web -p 8080:80 nginx:1.27
# open http://localhost:8080

# 2. An interactive throwaway shell (removed when you exit)
docker run -it --rm ubuntu:24.04 bash

# 3. A database with a password, a named volume and a restart policy
docker run -d --name pg \
  -e POSTGRES_PASSWORD=devpass \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  --restart unless-stopped \
  postgres:16

# 4. Run a one-off command in a tool image, mounting the current folder
docker run --rm -v "${PWD}:/work" -w /work python:3.12-slim python --version
PowerShell vs bash

Line continuation is \ in bash and a backtick ` in PowerShell. The current folder is $(pwd) in bash and ${PWD} in PowerShell. Or keep each command on one line.

Containers are cattle, not pets

Anything written inside a container's filesystem disappears when you docker rm it. Never exec in and hand-edit config for production. Change the Dockerfile or mount config, rebuild, and replace the container. Keep data in volumes (Chapter 12).

Chapter 7 · Images and containers

Images and layers

An image is not one big file. It is an ordered stack of read-only layers, each one a diff produced by an instruction in the Dockerfile. When a container starts, Docker adds one thin writable layer on top. The storage driver (overlay2 on Linux) merges them into one filesystem view.

Copy-on-write

When a container modifies a file that lives in a lower layer, the storage driver first copies it up into the writable layer, then changes the copy. The image itself never changes. Two consequences:

  • Deleting a file in a later layer does not shrink the image; the bytes still live in the earlier layer. Clean up in the same RUN that created the files.
  • Write-heavy data (databases, uploads) should go to a volume, which bypasses copy-on-write and is faster.

Tags, digests and inspecting layers

terminal
docker images                         # or: docker image ls
docker history python:3.12-slim       # one row per layer with size and instruction
docker image inspect python:3.12-slim # config, env, entrypoint, layer digests
docker pull python:3.12-slim@sha256:<digest>   # pin an exact, immutable build
docker image prune                    # remove dangling (untagged) images
docker system df                      # disk used by images, containers, volumes, cache

A tag (3.12-slim) is a movable label: the maintainer re-points it when they publish security fixes. A digest (sha256:…) is the content hash and never changes. Use tags for readability and digests when you need bit-for-bit reproducibility.

Tool: dive

dive shows every layer's added, changed and removed files and scores wasted space. Run it as a container: docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock wagoodman/dive myapi:1.0.

Bind to 0.0.0.0, not 127.0.0.1

Inside a container, 127.0.0.1 means "this container only". If your app listens on localhost, -p 8000:8000 forwards traffic to a port nobody is listening on, and you get "connection reset". Always bind servers to 0.0.0.0 in containers.

CMD vs ENTRYPOINT

Dockerfiledocker run imgdocker run img --port 9000
CMD ["uvicorn","main:app"]runs uvicorn main:apptries to run --port 9000 as the command (fails)
ENTRYPOINT ["uvicorn","main:app"]runs uvicorn main:appruns uvicorn main:app --port 9000
ENTRYPOINT ["uvicorn"]
CMD ["main:app"]		runs uvicorn main:appruns uvicorn --port 9000 (CMD replaced)

Rule of thumb: use CMD for apps (easy to override for debugging), ENTRYPOINT for images that behave like a CLI tool, and the pair when you need an entrypoint script (for example, run migrations then exec "$@").

Exec form vs shell form

CMD ["python","app.py"] (exec form, JSON array) runs your process directly as PID 1, so it receives SIGTERM from docker stop and can shut down gracefully. CMD python app.py (shell form) wraps it in /bin/sh -c; the shell often does not forward signals, so Docker waits 10 seconds and kills it. Use exec form. If your app does not reap child processes, add --init to docker run (or init: true in Compose).

Shortcut: docker init

Run docker init in a project folder. It detects the language (Python, Node, Go, Rust, Java, .NET, PHP) and generates a best-practice Dockerfile, compose.yaml and .dockerignore you can then edit.

The build cache

Docker caches every layer. On the next build it reuses a layer if the instruction and its inputs (for COPY, the files' checksums) are unchanged. The moment one layer changes, every layer after it is rebuilt. So the order of instructions decides how fast your rebuilds are.

BuildKit cache mounts

BuildKit (the default builder since Docker Engine 23) can keep a package manager's download cache between builds without putting it into the image. When you add one dependency, pip reuses everything already downloaded.

Dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
COPY . .

Cache rules worth memorising

  • Copy dependency manifests (requirements.txt, pyproject.toml + lock, package.json + lock) before the rest of the source.
  • Keep the build context small with .dockerignore: a changed .git folder or log file can bust COPY . ..
  • Combine apt-get update and apt-get install in one RUN, and clean up in the same line, so you never install from a stale cached index.
  • Use docker build --no-cache to force a clean rebuild (for example, to pick up base-image security fixes), or --pull to fetch a newer base.
  • In CI, export and import cache (--cache-to/--cache-from, Chapter 21) or every pipeline run is a cold build.
Dockerfile: installing OS packages correctly
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
Chapter 10 · Images and containers

Multi-stage builds

To build an app you often need compilers, headers and dev tools. To run it you need none of them. A multi-stage Dockerfile has several FROM lines; you build in a fat stage and copy only the finished artefacts into a slim final stage. Everything else is thrown away.

Example

Builder stage and runtime stage

Dockerfile (Python, multi-stage)
# syntax=docker/dockerfile:1

# ---------- Stage 1: build dependencies ----------
FROM python:3.12 AS builder
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /build
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# ---------- Stage 2: runtime ----------
FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"
RUN useradd --create-home --uid 10001 appuser
COPY --from=builder /opt/venv /opt/venv
WORKDIR /app
COPY --chown=appuser:appuser . .
USER appuser
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

For compiled languages the win is even bigger. A Go service can ship as a single static binary in an empty image:

Dockerfile (Go, final image a few MB)
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
USER nonroot
ENTRYPOINT ["/app"]

A tagging strategy that scales

  • Immutable release tags: 1.4.2 (semver) and the git commit SHA, sha-3f9c2ab. Never re-push a different image under these.

  • Add OCI labels so you can trace an image back to its source: LABEL org.opencontainers.image.source="https://github.com/acme/rag-api".

Example

Back up and restore a volume

Volumes have no "export" button. The trick: start a throwaway container that mounts both the volume and a host folder, and tar between them.

terminal (bash)
# Backup pgdata -> ./backup/pgdata.tgz
docker run --rm -v pgdata:/data:ro -v "$(pwd)/backup:/backup" alpine \
  tar czf /backup/pgdata.tgz -C /data .

# Restore into a new volume
docker run --rm -v pgdata_restored:/data -v "$(pwd)/backup:/backup" alpine \
  tar xzf /backup/pgdata.tgz -C /data

For databases, prefer the database's own dump tool while it runs: docker exec pg pg_dump -U postgres mydb > mydb.sql.

Data loss traps

docker compose down -v, docker volume prune and docker system prune --volumes delete volumes permanently. Anonymous volumes (created by VOLUME in a Dockerfile without a name) are easy to lose: always give important volumes a name.

Default bridge vs user-defined bridge

Containers on the built-in bridge network can only reach each other by IP. On a network you create (docker network create appnet) Docker runs an embedded DNS server, so containers find each other by container name. Always create your own network (Compose does this for you automatically).

Port publishing, precisely

  • -p 8080:80 = host 8080 → container 80, on all host interfaces (reachable from your LAN).
  • -p 127.0.0.1:5432:5432 = only from the host itself. Use this for dev databases.
  • -p 8080:80/udp for UDP. -P publishes every EXPOSEd port on random host ports.
  • Container-to-container traffic on the same network needs no -p at all; use the container port directly (db:5432).
  • From a container, reach a service on your host machine with host.docker.internal (built into Docker Desktop; on Linux add --add-host=host.docker.internal:host-gateway).
Security: published ports and Linux firewalls

On Linux, Docker writes its own iptables rules, so a port published with -p 5432:5432 can be reachable from the internet even if ufw says it is blocked. Bind to 127.0.0.1, do not publish databases at all in production, and put a reverse proxy in front of web services.

Environment variables, config and secrets

Follow the twelve-factor rule: the same image runs in dev, staging and prod; only configuration changes, and configuration comes from the environment. Never bake environment-specific values into the image.

terminal

# From a file (one KEY=value per line, no quotes needed)
docker run --env-file .env myapi:1.0

# Pass through a variable from your shell without writing its value

.env (never commit; commit a .env.example instead)

Secrets: what not to do

Never

ENV API_KEY=sk-… or ARG API_KEY in a Dockerfile, or COPY .env .. Values end up in image layers and in docker history / docker inspect, forever, for anyone who can pull the image.

Instead

Runtime env vars from a secret store, Compose/Swarm secrets mounted as files under /run/secrets/, or BuildKit secret mounts for build-time credentials.

Dockerfile: use a secret during build without storing it
# syntax=docker/dockerfile:1
FROM python:3.12-slim
# The token is mounted only for this RUN and never written to a layer
RUN --mount=type=secret,id=pip_token \
    PIP_INDEX_URL="https://__token__:$(cat /run/secrets/pip_token)@pypi.example.com/simple" \
    pip install private-package
terminal
docker build --secret id=pip_token,src=./pip_token.txt -t myapi:1.0 .
compose.yaml: runtime secret as a file
services:
  api:
    image: myapi:1.0
    secrets:
      - db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password   # app reads the file
secrets:
  db_password:
    file: ./secrets/db_password.txt
The *_FILE convention

Many official images (postgres, mysql, mariadb) accept POSTGRES_PASSWORD_FILE=/run/secrets/db_password instead of the plain variable. Use the same pattern in your own apps: environment variables can leak through docker inspect, crash dumps and child processes; files are easier to lock down.

Variables and .env

Compose automatically reads a .env file next to compose.yaml and substitutes ${VAR} in the YAML. Defaults and required checks are built in:

Alpine and Python

Alpine uses musl instead of glibc. Many Python packages (numpy, pandas, torch, psycopg) ship prebuilt manylinux (glibc) wheels; on Alpine pip may have to compile from source, making builds slow and images bigger. For Python, start with -slim; consider distroless or Chainguard/Docker Hardened Images when you need minimal attack surface.

Optimisation checklist

  1. Pick a slim base and pin it: python:3.12-slim, not python or latest.
  2. Multi-stage: build tools stay in the builder (Chapter 10).
  3. Order layers for cache hits; copy manifests first (Chapter 9).
  4. Clean up in the same RUN: --no-install-recommends, rm -rf /var/lib/apt/lists/*, pip install --no-cache-dir.
  5. .dockerignore everything not needed: .git, venvs, datasets, notebooks, tests (unless you test in the image).
  6. Do not ship models or datasets inside the image if they are large and change independently; mount a volume or download at start (Chapter 23).
  7. Measure: docker images, docker history, dive.
Chapter 18 · Production

Security

Containers share the host kernel, so a compromised container is closer to the host than a compromised VM. Defence comes in layers: a minimal image, a least-privilege runtime, a hardened host, and scanning in CI.

Image hardening

Dockerfile: hardened runtime stage
FROM python:3.12-slim
# Fixed, non-root UID/GID (high numbers avoid clashing with host users)
RUN groupadd --gid 10001 app && useradd --uid 10001 --gid app --no-create-home app
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY --chown=app:app . .
ENV PATH="/opt/venv/bin:$PATH"
USER 10001:10001
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request,sys; urllib.request.urlopen('http://127.0.0.1:8000/health'); sys.exit(0)"
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Runtime hardening

terminal
# --read-only + --tmpfs : immutable root filesystem, writable /tmp only
# --cap-drop ALL        : drop every Linux capability
# no-new-privileges     : block setuid privilege escalation
docker run -d --name api \
  --read-only --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --pids-limit 200 --memory 512m --cpus 1 \
  -u 10001:10001 \
  -p 127.0.0.1:8000:8000 \
  myapi:1.0
compose.yaml equivalent
services:
  api:
    image: myapi:1.0
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    user: "10001:10001"
    pids_limit: 200
    mem_limit: 512m
    cpus: 1

Security checklist

  • Run as a non-root user (USER). Never use --privileged unless you truly need device access.
  • Never mount /var/run/docker.sock into an app container: it is full root on the host.
  • Use official or verified base images, pinned by tag (and digest for critical services). Rebuild regularly to pick up patches.
  • Scan images in CI and fail on critical CVEs: docker scout cves myapi:1.0 or trivy image myapi:1.0.
  • Lint Dockerfiles with hadolint: docker run --rm -i hadolint/hadolint < Dockerfile.
  • No secrets in images: use runtime secrets (Chapter 14). Check with docker history --no-trunc.
  • Publish only the ports you need; bind internal services to private networks.
  • Generate an SBOM and provenance: docker buildx build --sbom=true --provenance=mode=max …, and sign images (cosign / Docker Content Trust) for supply-chain integrity.
  • On the host: keep Docker and the kernel updated; consider rootless mode or userns-remap; follow the CIS Docker Benchmark.
  • For untrusted code (e.g. LLM-generated code execution), add a stronger sandbox: gVisor (--runtime=runsc), Kata Containers or Firecracker microVMs.
terminal: scanning
docker scout quickview myapi:1.0          # summary of CVEs and base-image advice
docker scout cves --only-severity critical,high myapi:1.0
docker scout recommendations myapi:1.0    # suggests a better base image

# Trivy as a container (no install needed)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image myapi:1.0

Resource limits

Without limits, one leaking container can starve the whole host. Set memory and CPU on every production service.

terminal
docker run -d --memory 1g --memory-swap 1g --cpus 2 --pids-limit 300 myapi:1.0
docker stats --no-stream        # check real usage before choosing limits

When a container exceeds its memory limit, the kernel's OOM killer kills it: exit code 137 and "OOMKilled": true in docker inspect.

Health checks

A HEALTHCHECK lets Docker report healthy/unhealthy in docker ps. Compose uses it for depends_on; Swarm replaces unhealthy tasks. Keep the check cheap and local (an HTTP /health endpoint), and remember slim images do not include curl: use the app's language or install a tiny tool.

Logs

Write logs to stdout/stderr, not files. Docker captures them (docker logs) and ships them through a logging driver. The default json-file driver grows without bound unless you rotate it:

/etc/docker/daemon.json (Linux) · Docker Desktop: Settings → Docker Engine
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

Other drivers send logs to journald, syslog, fluentd, gelf, awslogs or gcplogs. A common open-source stack: Promtail/Alloy → Loki → Grafana.

Monitoring

  • docker stats for a quick look.
  • cAdvisor exports per-container CPU, memory, network and disk metrics → Prometheus → Grafana dashboards and alerts.
  • Instrument your app (OpenTelemetry) for request latency, errors and traces.

Graceful shutdown and zero-downtime updates

  • docker stop sends SIGTERM, waits (10 s default; stop_grace_period in Compose), then SIGKILL. Handle SIGTERM: finish in-flight requests, close DB connections.
  • On a single host with Compose, an update is docker compose pull && docker compose up -d: changed services are recreated, others untouched. Expect a few seconds of downtime per service unless you run two replicas behind a reverse proxy (Traefik, Caddy, Nginx).
  • For real rolling updates and self-healing across machines, use an orchestrator (Chapter 22).

CI/CD with Docker

The image is the build artefact. CI builds it once, tests and scans that exact image, pushes it to a registry with an immutable tag, and every environment deploys the same digest.

Example

Push to deploy

.github/workflows/docker.yml
name: docker

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]
  pull_request:

permissions:
  contents: read
  packages: write          # push to ghcr.io with GITHUB_TOKEN

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-qemu-action@v3      # emulate arm64 for multi-arch
      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        if: github.event_name != 'pull_request'
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha
            type=ref,event=branch

      # 1) Run the test stage inside Docker
      - name: Test
        uses: docker/build-push-action@v6
        with:
          context: .
          target: test
          cache-from: type=gha
          cache-to: type=gha,mode=max

      # 2) Build the runtime image locally and scan it
      - name: Build for scan
        uses: docker/build-push-action@v6
        with:
          context: .
          load: true
          tags: scan-me:ci
          cache-from: type=gha
      - name: Scan (fail on critical/high)
        run: |
          docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
            aquasec/trivy image --exit-code 1 --severity CRITICAL,HIGH --ignore-unfixed scan-me:ci

      # 3) Build multi-arch and push (layers come from cache)
      - name: Push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          sbom: true
          provenance: mode=max
          cache-from: type=gha
          cache-to: type=gha,mode=max

1. The application

app/main.py
import hashlib
import os
from contextlib import asynccontextmanager

import httpx
import psycopg
import redis.asyncio as redis
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

# All configuration comes from the environment (twelve-factor)
DATABASE_URL = os.environ["DATABASE_URL"]
REDIS_URL = os.environ.get("REDIS_URL", "redis://redis:6379/0")
OLLAMA_URL = os.environ.get("OLLAMA_URL", "http://ollama:11434")
MODEL = os.environ.get("LLM_MODEL", "llama3.2")
CACHE_TTL = int(os.environ.get("CACHE_TTL", "3600"))


class Ask(BaseModel):
    question: str


async def db():
    return await psycopg.AsyncConnection.connect(DATABASE_URL, autocommit=True)


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.redis = redis.from_url(REDIS_URL, decode_responses=True)
    app.state.http = httpx.AsyncClient(base_url=OLLAMA_URL, timeout=120)
    async with await db() as conn:
        await conn.execute("CREATE EXTENSION IF NOT EXISTS vector")  # ready for RAG later
        await conn.execute(
            """CREATE TABLE IF NOT EXISTS qa (
                   id SERIAL PRIMARY KEY,
                   question TEXT NOT NULL,
                   answer TEXT NOT NULL,
                   model TEXT NOT NULL,
                   created_at TIMESTAMPTZ DEFAULT now())"""
        )
    yield
    await app.state.http.aclose()
    await app.state.redis.aclose()


app = FastAPI(title="AI Q&A service", lifespan=lifespan)


@app.get("/health")
async def health():
    await app.state.redis.ping()
    return {"status": "ok", "model": MODEL}


@app.post("/ask")
async def ask(body: Ask):
    key = "qa:" + hashlib.sha256(f"{MODEL}:{body.question}".encode()).hexdigest()
    if cached := await app.state.redis.get(key):
        return {"answer": cached, "cached": True}

    r = await app.state.http.post(
        "/api/generate",
        json={"model": MODEL, "prompt": body.question, "stream": False},
    )
    if r.status_code != 200:
        raise HTTPException(502, f"LLM error: {r.text[:200]}")
    answer = r.json()["response"]

    await app.state.redis.set(key, answer, ex=CACHE_TTL)
    async with await db() as conn:
        await conn.execute(
            "INSERT INTO qa (question, answer, model) VALUES (%s, %s, %s)",
            (body.question, answer, MODEL),
        )
    return {"answer": answer, "cached": False}


@app.get("/history")
async def history(limit: int = 10):
    async with await db() as conn:
        cur = await conn.execute(
            "SELECT question, answer, model, created_at FROM qa ORDER BY id DESC LIMIT %s",
            (limit,),
        )
        rows = await cur.fetchall()
    return [{"question": q, "answer": a, "model": m, "at": t.isoformat()} for q, a, m, t in rows]

4. Run it

  1. Create your env file: Copy-Item .env.example .env (PowerShell) or cp .env.example .env, and set a real password.
  2. Start everything: docker compose up -d --build. The first run downloads the model (about 2 GB for llama3.2); follow it with docker compose logs -f model-init.
  3. Check status: docker compose ps. api, db, redis and ollama should show healthy; model-init should show exited (0).
  4. Ask a question (below). Ask the same question again: the second answer returns instantly with "cached": true.
  5. Look at the data: curl localhost:8000/history and docker compose exec db psql -U app -c "select count(*) from qa;".
  6. Develop with hot sync: docker compose watch, then edit app/main.py.
  7. Run the tests in Docker: docker build --target test .

5. Ship it

  1. Push to GitHub with the workflow from Chapter 21: it runs the test stage, scans, and pushes ghcr.io/acme/aiqa-api:<version> for amd64 and arm64.
  2. On the server: copy compose.yaml, compose.prod.yaml and a real .env (with TAG=1.0.0) to /opt/aiqa.
  3. Deploy: docker compose -f compose.yaml -f compose.prod.yaml pull && docker compose -f compose.yaml -f compose.prod.yaml up -d.
  4. Put Caddy or Nginx in front for HTTPS, and schedule a nightly pg_dump backup of the db service.

Best practices from production

Images

Slim, pinned base images · multi-stage · manifests copied before code · one RUN per logical step with cleanup · .dockerignore · OCI labels · rebuild weekly for patches.

Runtime

One process per container · exec-form CMD · handle SIGTERM · logs to stdout · healthcheck · memory/CPU limits · restart policy · bind servers to 0.0.0.0.

Data

State in named volumes or managed databases · never in the writable layer · tested backups · treat containers as disposable.

Config

Same image for every environment · config via env vars and files · secrets from a secret store or /run/secrets · .env never committed.

Security

Non-root USER · cap_drop: [ALL] · read-only root FS · no docker.sock · scan + lint in CI · publish minimal ports · SBOM and signatures.

Delivery

Build once in CI · immutable tags (semver + SHA) · deploy by tag/digest, never latest · multi-arch when needed · cache in CI.

Anti-patterns to avoid

Anti-patternWhy it hurtsDo this instead
FROM ubuntu + install everythingHuge, slow, many CVEsLanguage-specific slim base, multi-stage
COPY . . before installing depsEvery edit reinstalls everythingCopy manifests, install, then copy code
SSH server inside the containerExtra attack surface, pets not cattledocker exec
Several services in one container with supervisordCannot scale, restart or log them independentlyOne service per container + Compose
Secrets in ENV/ARGVisible in history and inspectRuntime secrets, BuildKit secret mounts
Deploying :latestUnknown version, no reliable rollbackImmutable version tags
Running as rootEscape = root on the hostUSER 10001
Editing a running container by handLost on recreate, undocumentedChange Dockerfile/config, rebuild, redeploy

Glossary

Bind mountA host file or folder mounted into a container at a path.
Bridge networkDocker's default single-host virtual network; user-defined bridges add DNS by name.
Build contextThe files sent to the builder (the . in docker build .), filtered by .dockerignore.
BuildKit / buildxDocker's modern build engine and its CLI plugin: parallel stages, cache and secret mounts, multi-platform.
cgroupsKernel feature that limits and measures CPU, memory, I/O and processes.
ComposeTool and YAML format for defining and running multi-container apps.
ContainerA running (or stopped) instance of an image: an isolated process with its own filesystem view, network and limits.
containerd / runcThe container runtime daemon and the low-level OCI runtime Docker uses underneath.
Copy-on-writeFiles from read-only layers are copied to the writable layer only when modified.
DigestContent hash (sha256:…) that identifies an exact image immutably.
DistrolessImages with only the app runtime: no shell or package manager.
DockerfileText file of instructions to build an image.
Docker Engine / daemondockerd: the background service that builds images and runs containers.
Docker DesktopDesktop app for Windows/macOS/Linux bundling the engine (in a light VM), CLI, Compose and a GUI.
ImageRead-only, layered template containing an app and its environment.
LayerOne filesystem diff in an image, produced by a Dockerfile instruction.
Multi-stage buildA Dockerfile with several FROMs, copying only artefacts into the final stage.
NamespaceKernel feature that gives a process its own view of PIDs, network, mounts, hostname, users.
OCIOpen Container Initiative: open standards for image format, runtime and distribution.
OrchestratorSystem that schedules containers across many hosts (Kubernetes, Swarm).
Publish (port)Map a host port to a container port with -p.
Registry / repositoryServer that stores images (Docker Hub, GHCR) / a named collection of tags in it.
SBOMSoftware Bill of Materials: list of packages inside an image.
TagHuman-readable, movable label for an image version (1.4.2, latest).
tmpfsIn-memory mount, never written to disk.
VolumeDocker-managed persistent storage, independent of container lifecycle.
WSL 2Windows Subsystem for Linux: the real Linux kernel Docker Desktop uses on Windows.
