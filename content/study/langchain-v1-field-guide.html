LangChain v1 Field Guide

One document that takes you from "what is LangChain?" to building, controlling, testing and shipping production agents with LangChain v1. Every chapter has a plain explanation, a diagram where it helps, and runnable code.

How to read this

Parts I–III are the core: read them in order. Parts IV–VI can be read as needed. Part VII ties everything together in one project. Code targets langchain>=1.0 on Python 3.10+. Model names are examples; swap in whichever provider and model you use.

Chapter 1 · Foundations

What is LangChain v1?

LangChainnoun · open-source framework

An open-source framework for building applications and agents powered by large language models (LLMs). It gives you one standard interface to any model provider, a library of integrations (tools, vector stores, loaders), and a ready-made agent you can customise. In v1, the centre of LangChain is create_agent: a production-ready agent loop built on the LangGraph runtime and customised through middleware.

LangChain 1.0 was released in October 2025 as the first stable major version. The team kept the parts developers actually used, removed or relocated the rest, and committed to no breaking changes until 2.0. The short version of what changed:

  • One way to build agents. from langchain.agents import create_agent replaces LangGraph's create_react_agent. The older AgentExecutor and initialize_agent now live in langchain-classic.
  • Middleware lets you hook into every step of the agent loop (before the model call, around tool calls, after the agent finishes) for summarisation, human approval, PII redaction, retries and more.
  • Built on LangGraph. Every agent gets persistence, streaming, human-in-the-loop and time travel for free, because it runs as a LangGraph graph.
  • Standard content blocks. message.content_blocks gives the same shape for text, reasoning, tool calls and images across supported providers (OpenAI, Anthropic, Google GenAI, AWS and Ollama, with more being added). Citations appear as annotations on text blocks.
  • A slimmer package. The langchain namespace now holds only agents, models, messages, tools and embeddings. Old chains, retrievers and the hub moved to langchain-classic.

Chapter 2 · Foundations

The problem LangChain solves

Calling an LLM once is easy. Building a reliable application around it is not. As soon as you go past a single prompt you hit the same set of problems every team hits:

ProblemWithout a frameworkLangChain v1 answer
Provider lock-inEach SDK (OpenAI, Anthropic, Google, Ollama) has its own request and response format. Switching means rewriting.init_chat_model("provider:model") with one interface: invoke, stream, batch, bind_tools.
Tool callingHand-write JSON schemas, parse tool calls, run functions, feed results back, loop until done.@tool builds the schema from your function. create_agent runs the loop.
MemoryStore and trim conversation history yourself. Context windows overflow.Checkpointers save each thread. SummarizationMiddleware trims old turns.
Using your own dataWrite loaders for PDFs, web pages and databases; chunk, embed and search them.Hundreds of document loaders, text splitters, embedding models and vector stores behind standard interfaces.
Reliable outputAsk for JSON and hope. Parse, validate, retry.response_format=MySchema returns a validated Pydantic object.
Safety and controlAgents can send emails or delete data with no checkpoint.HumanInTheLoopMiddleware pauses for approval; limits and PII middleware enforce policy.
DebuggingPrint statements across a multi-step loop.LangSmith tracing shows every model call, tool call, token count and latency.

The proof is how little code a working agent takes:

first_agent.py
from langchain.agents import create_agent

def get_weather(city: str) -> str:
    """Get the current weather for a city."""
    return f"It is always sunny in {city}!"

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",   # any "provider:model" string
    tools=[get_weather],
    system_prompt="You are a helpful assistant.",
)

result = agent.invoke({"messages": [{"role": "user", "content": "Weather in Pune?"}]})
print(result["messages"][-1].content)
Chapter 3 · Foundations

Where to use LangChain (and where not to)

Customer support agents

Look up orders, search the help centre, open tickets, hand off to a human for refunds.

Chat with your documents

RAG over PDFs, wikis, Confluence, SharePoint or a database, with cited answers.

Internal copilots

Agents that query SQL, call internal APIs, draft emails and fill forms for employees.

Data extraction

Turn invoices, resumes or contracts into validated structured records.

Research assistants

Search the web, read pages, plan, and write a report (Deep Agents).

Multi-model products

Apps that must switch providers by cost, region or capability, or fall back on outage.

When something else fits better

A single prompt, one provider

If you only call one model once with a fixed prompt, the provider's SDK is simpler.

Complex, deterministic workflows

Branching, parallel steps and loops you design yourself: use LangGraph directly (Chapter 22).

Long autonomous tasks

Multi-hour work with planning and a file system: start with Deep Agents (Chapter 23).

Rule of thumb

The official docs now suggest Deep Agents as the batteries-included starting point, create_agent when you want to build and customise the agent harness yourself, and LangGraph when you need to mix fixed workflow steps with agent steps. This guide teaches create_agent first because Deep Agents is built on it: once you understand it, Deep Agents is easy to pick up.

Chapter 6 · Building blocks

Chat models

A chat model takes a list of messages and returns an AIMessage. LangChain gives every provider the same interface, so the rest of your code never changes when you switch.

Two ways to create a model

models.py
# 1. Universal initialiser: "provider:model"
from langchain.chat_models import init_chat_model

model = init_chat_model(
    "anthropic:claude-sonnet-4-6",
    temperature=0,        # 0 = deterministic, higher = more creative
    max_tokens=1024,      # cap the answer length
    timeout=30,           # seconds
    max_retries=6,        # default; retries 429 / 5xx / network errors with backoff
)                         # (raise to 10-15 for long-running agents)

# 2. Provider class, when you need provider-specific options
from langchain_openai import ChatOpenAI
gpt = ChatOpenAI(model="gpt-5.4-mini", temperature=0)

# Local model, no API key, via Ollama
local = init_chat_model("ollama:llama3.1")

The five methods you will use

model_methods.py
# invoke: one request, full answer
response = model.invoke("Explain RAG in one sentence.")
print(response.content)          # the text
print(response.usage_metadata)   # {'input_tokens': 14, 'output_tokens': 31, ...}

# stream: tokens as they arrive (for chat UIs)
for chunk in model.stream("Write a haiku about graphs."):
    print(chunk.text, end="", flush=True)

# batch: many independent requests in parallel
answers = model.batch(["What is 2+2?", "Capital of Japan?"])

# async versions: ainvoke, astream, abatch
# response = await model.ainvoke("Hello")

# bind_tools / with_structured_output: see Chapters 9 and 11

Messages and standard content blocks

Messages are the unit of conversation. There are four types you need to know:

ClassRoleWho creates it
SystemMessagesystemYou: instructions and persona
HumanMessageuserThe user's input
AIMessageassistantThe model: text and/or tool_calls
ToolMessagetoolThe agent, after running a tool; links back via tool_call_id
messages.py
from langchain.messages import SystemMessage, HumanMessage, AIMessage

conversation = [
    SystemMessage("You are a concise travel assistant."),
    HumanMessage("Suggest one city in Japan."),
    AIMessage("Kyoto."),
    HumanMessage("Why that one?"),
]
reply = model.invoke(conversation)

# Dict shorthand works everywhere too:
reply = model.invoke([{"role": "user", "content": "Hi"}])

Standard content blocks (new in v1)

Providers return rich content in different shapes: Anthropic has "thinking" blocks, OpenAI has "reasoning" items, both have tool calls and citations. message.content_blocks normalises them into one list of typed dictionaries, so your UI code handles every provider the same way.

content_blocks.py
response = model.invoke("What is 17 * 23? Think first.")

for block in response.content_blocks:
    if block["type"] == "reasoning":
        print("THINKING:", block.get("reasoning"))
    elif block["type"] == "text":
        print("ANSWER:", block["text"])
    elif block["type"] == "tool_call":
        print("TOOL:", block["name"], block["args"])

print(response.text)   # v1: .text is a property (it was a method .text() in v0)
Example

Many providers, one standard shape

Each provider formats its replies differently. Standard content blocks turn them all into the same block types, so your code reads every provider the same way.

Remember

Content blocks = how content is represented. Tools = what actions the agent can perform. Provider / model = which LLM is used. Content blocks are not the way to connect multiple tools or API keys.

  • The old .text() form still works with a deprecation warning and will be removed in v2.
  • Standard blocks are not written into .content by default. To opt in, set the environment variable LC_OUTPUT_VERSION=v1 or pass output_version="v1" to init_chat_model.
  • ToolMessage has an artifact field for data that should be kept but not sent to the model.

    {"type": "image", "url": "https://example.com/photo.jpg"},
    # image blocks also accept "base64" + "mime_type", or a provider "file_id"
])
Chapter 8 · Building blocks

Prompts and LCEL

In v1, most agents only need a system_prompt string. Prompt templates and the LangChain Expression Language (LCEL) still live in langchain_core and remain useful for fixed, non-agent pipelines: summarisers, classifiers, translators.

prompt_template.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ("system", "You translate text into {language}. Reply with the translation only."),
    ("user", "{text}"),
])

# LCEL: the | operator pipes the output of one step into the next
chain = prompt | model | StrOutputParser()

print(chain.invoke({"language": "Hindi", "text": "Good morning"}))

Everything joined with | is a Runnable, so the chain automatically gets invoke, stream, batch and async versions.

Writing a good system prompt for an agent

prompts.py
SUPPORT_PROMPT = """You are Asha, a support agent for AutoPlant.

## Goal
Resolve the customer's issue in as few turns as possible.

## Tools
- Use `lookup_order` before answering any question about an order.
- Use `search_kb` for product and policy questions. Cite the article title.
- Never promise a refund. Use `escalate_to_human` for refunds.

## Style
Short paragraphs. Plain language. Ask one clarifying question when unsure.
"""
Prompt checklist

Role, goal, when to use each tool, what never to do, output style. Put rules about tools in the prompt and in each tool's docstring.

Chapter 9 · Building blocks

Tools

A tool is a Python function the model can ask to run. The model never runs code itself: it returns a tool call (name + arguments), your agent runs the function, and the result goes back to the model as a ToolMessage.

Example

What a tool is, and what it is not

A tool is a callable operation the agent is allowed to request: a Python function, a database operation, an API wrapper, a calculator, a search function, or a controlled business action. It is easy to confuse with these other things:

ThingMeaning
ToolAn action the agent can invoke
API keyAn authentication credential (a password for a provider)
ModelThe LLM used for reasoning and generating text
Content blockThe standard representation of message / model content

Defining tools with @tool

tools.py
from langchain.tools import tool

@tool
def search_database(query: str, limit: int = 10) -> str:
    """Search the customer database for records matching the query.

    Args:
        query: Search terms, e.g. a name or email.
        limit: Maximum number of results to return.
    """
    return f"Found {limit} results for '{query}'"

# The name, docstring and type hints become the schema the model sees:
print(search_database.name)          # search_database
print(search_database.args)          # {'query': {...}, 'limit': {...}}
print(search_database.invoke({"query": "Ravi"}))
The docstring is the prompt

The model chooses tools from their name and description alone. Write the docstring as instructions: what it does, when to use it, and what each argument means.

Rich argument schemas with Pydantic

tools_pydantic.py
from typing import Literal
from pydantic import BaseModel, Field

class WeatherInput(BaseModel):
    location: str = Field(description="City name or coordinates")
    units: Literal["celsius", "fahrenheit"] = Field(default="celsius")
    include_forecast: bool = Field(default=False, description="Add a 5-day forecast")

@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather and an optional forecast."""
    temp = 22 if units == "celsius" else 72
    return f"{location}: {temp}°{units[0].upper()}" + (" | 5-day: sunny" if include_forecast else "")

Tools that read state, context and memory: ToolRuntime

Add a parameter typed ToolRuntime and LangChain injects it at run time. The model never sees this parameter.

tools_runtime.py
from dataclasses import dataclass
from langchain.tools import tool, ToolRuntime

@dataclass
class Context:
    user_id: str

@tool
def get_my_orders(runtime: ToolRuntime[Context]) -> str:
    """Get the current user's recent orders."""
    user_id = runtime.context.user_id          # per-request data (Chapter 14)
    history = runtime.state["messages"]        # the conversation so far
    store = runtime.store                      # long-term memory (Chapter 13)
    runtime.stream_writer({"status": "fetching orders"})  # custom stream event
    return f"Orders for {user_id}: #1042 (shipped), #1051 (processing)"

Other runtime fields: runtime.config, runtime.tool_call_id, and (with langgraph>=1.1.5) runtime.execution_info (thread ID, run ID, attempt number) and runtime.server_info (assistant, graph and user; None outside LangGraph Server).

Reserved names

config and runtime cannot be used as your own tool argument names. ToolRuntime replaces the older InjectedState, InjectedStore, InjectedToolCallId and get_runtime().

More @tool options and return types

tool_options.py
from langchain.messages import ToolMessage
from langgraph.types import Command

@tool("web_search")                                   # custom name
def search(query: str) -> str:
    """Search the web for information."""
    return f"Results for {query}"

@tool("calculator", description="Evaluate a maths expression.")  # custom description
def calc(expression: str) -> str:
    return str(eval(expression))   # demo only: never eval untrusted input

@tool(return_direct=True)                             # agent stops and returns this output
def final_quote(product: str) -> str:
    """Return the official price quote for a product."""
    return f"{product}: ₹4,999"

@tool
def set_ticket(ticket_id: str, runtime: ToolRuntime) -> Command:
    """Attach a support ticket ID to this conversation."""
    return Command(update={
        "ticket_id": ticket_id,                       # updates agent state
        "messages": [ToolMessage(f"Ticket {ticket_id} attached",
                                 tool_call_id=runtime.tool_call_id)],  # required
    })

Tools may also return a dict or a list of multimodal content blocks. A Command return must include a ToolMessage with the matching tool_call_id, otherwise the agent raises a ValueError.

model_with_tools = model.bind_tools([get_weather])

Chapter 10 · Agents

create_agent: the heart of v1

An agent is a model that decides, step by step, which tools to call until it can answer. This is the ReAct pattern (Reason + Act). create_agent builds that loop as a LangGraph graph.

Full signature, explained

agent_full.py
from langchain.agents import create_agent

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",  # string or a model instance
    tools=[search_database, get_weather], # list of tools (or [] for none)
    system_prompt=SUPPORT_PROMPT,         # str or SystemMessage
    response_format=None,                 # schema type, or ToolStrategy / ProviderStrategy (Ch. 11)
    middleware=[],                        # list of middleware (Ch. 16)
    checkpointer=None,                    # short-term memory (Ch. 12)
    store=None,                           # long-term memory (Ch. 13)
    context_schema=None,                  # type of runtime context (Ch. 14)
    state_schema=None,                    # extra state fields (Ch. 12)
    name="support_agent",                 # useful in multi-agent systems
    # advanced: interrupt_before, interrupt_after, debug, cache, transformers
)

Real-world example

Practical logistics agent

The Logistics TAT Assistant from Chapter 1, as code. Each function is one tool. The one-line docstring under each function is required: it is what the model reads to decide when to use that tool.

logistics_agent.py
from langchain.agents import create_agent
from langchain_groq import ChatGroq

model = ChatGroq(model="openai/gpt-oss-120b", temperature=0)

def query_vehicle_data(date: str) -> str:
    """Get the vehicle records for a date."""
    return "1500 vehicles"

def calculate_stage_tat(records: str) -> dict:
    """Calculate yard, plant and total TAT from vehicle records."""
    return {
        "yard_tat": "00:48",
        "plant_tat": "03:12",
        "total_tat": "04:00"
    }

def get_kpi_summary() -> str:
    """Get the TAT KPI summary compared with the target."""
    return "Plant TAT is 12% above target."

agent = create_agent(
    model=model,
    tools=[
        query_vehicle_data,
        calculate_stage_tat,
        get_kpi_summary
    ],
    system_prompt="You are a logistics analytics assistant."
)

response = agent.invoke({
    "messages": [{"role": "user", "content": "Why was plant TAT high yesterday?"}]
})
print(response["messages"][-1].content)

The functions return fixed sample values so you can run it right away. In a real project, replace their bodies with queries to your own vehicle database.

Handling tool errors

By default, a tool exception is raised. Usually you want the model to see the error and try again. Use the wrap_tool_call middleware (more in Chapter 16):

from langchain.messages import ToolMessage

def handle_tool_errors(request, handler):
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(
            content=f"Tool error: {e}. Check the arguments and try again.",
            tool_call_id=request.tool_call["id"],

Long-term memory (across conversations)

Short-term memory belongs to one thread. Long-term memory belongs to a user or organisation and is shared by every thread. It lives in a store: a key-value database organised by namespaces.

long_term_memory.py
from dataclasses import dataclass
from langgraph.store.memory import InMemoryStore
from langchain.tools import tool, ToolRuntime

@dataclass
class Context:
    user_id: str

@tool
def save_preference(key: str, value: str, runtime: ToolRuntime[Context]) -> str:
    """Remember a user preference for future conversations."""
    runtime.store.put(("prefs", runtime.context.user_id), key, {"value": value})
    return f"Saved {key} = {value}"

@tool
def get_preferences(runtime: ToolRuntime[Context]) -> str:
    """Recall everything we know about the user's preferences."""
    items = runtime.store.search(("prefs", runtime.context.user_id), limit=100)  # default limit is 10
    return "\n".join(f"{i.key}: {i.value['value']}" for i in items) or "No preferences yet."

store = InMemoryStore()   # production: PostgresStore
agent = create_agent(model, tools=[save_preference, get_preferences],
                     store=store, context_schema=Context)

agent.invoke({"messages": [{"role": "user", "content": "I prefer answers in Hindi."}]},
             context=Context(user_id="42"))
# ...a week later, in a brand-new thread:
agent.invoke({"messages": [{"role": "user", "content": "Explain RAG."}]},
             context=Context(user_id="42"))

inputs = {"messages": [{"role": "user", "content": "Weather in Delhi and Goa?"}]}

# Step-by-step progress
for chunk in agent.stream(inputs, stream_mode="updates"):
    for step, data in chunk.items():
        print(f"[{step}]", data["messages"][-1].content_blocks)

# Token-by-token
for token, metadata in agent.stream(inputs, stream_mode="messages"):
    if metadata["langgraph_node"] == "model" and token.text:
        print(token.text, end="", flush=True)

    print(mode, chunk)

Newer streaming formats

The code above uses the default format, which yields tuples. The current docs show two newer options:

  • version="v2" on stream gives every chunk the same dict shape: {"type": ..., "ns": ..., "data": ...}.
  • agent.stream_events(..., version="v3") (new in LangChain 1.3) is the recommended API for new apps. It gives typed streams for messages, tool calls and values.
streaming_v2_v3.py
# v2: uniform dict chunks
for chunk in agent.stream(inputs, stream_mode="messages", version="v2"):
    if chunk["type"] == "messages":
        token, metadata = chunk["data"]
        if metadata["langgraph_node"] == "model" and token.text:
            print(token.text, end="", flush=True)

# v3 event streaming: recommended for new applications (langchain 1.3+)
stream = agent.stream_events(inputs, version="v3")
for kind, item in stream.interleave("messages", "tool_calls"):
    if kind == "messages":
        for t in item.text:
            print(t, end="", flush=True)
    else:
        print(f"\nTool call: {item.tool_name}({item.input}) -> {item.output}")

Defaults worth knowing

PII: built-in types are email, credit_card, ip, mac_address, url; add your own with detector=. apply_to_input is on by default; apply_to_output and apply_to_tool_results are off. strategy="block" raises an exception, so catch it.
Retries: ToolRetryMiddleware / ModelRetryMiddleware default to max_retries=2, backoff_factor=2.0, initial_delay=1.0, max_delay=60.0, jitter=True, on_failure="continue".
Limits: ToolCallLimitMiddleware exit_behavior defaults to "continue" (also "error", "end"). ModelCallLimitMiddleware takes "end" or "error"; its thread_limit needs a checkpointer.

Order matters

Middleware runs like layers of an onion. before_* hooks run first to last; after_* hooks run last to first; the first wrap_* middleware is the outermost wrapper.

Writing custom middleware: classes

Use a class when the middleware needs configuration, several hooks or its own state fields.

custom_class.py
import time
from typing_extensions import NotRequired
from langchain.agents.middleware import AgentMiddleware, AgentState

class TimingState(AgentState):
    model_ms: NotRequired[list[float]]   # extra fields should be optional

class TimingMiddleware(AgentMiddleware[TimingState]):
    state_schema = TimingState          # adds a field to agent state

    def __init__(self, slow_ms: float = 5000):
        super().__init__()
        self.slow_ms = slow_ms

    def wrap_model_call(self, request, handler):
        start = time.perf_counter()
        response = handler(request)
        ms = (time.perf_counter() - start) * 1000
        if ms > self.slow_ms:
            print(f"Slow model call: {ms:.0f} ms")
        return response

    def after_agent(self, state, runtime):
        print("Run finished with", len(state["messages"]), "messages")
        return None

agent = create_agent(model, tools=[], middleware=[TimingMiddleware(slow_ms=3000)])

In class hooks, allow jumps with the @hook_config(can_jump_to=["end"]) decorator. jump_to can be "end", "tools" or "model". Besides state_schema, a middleware class can also declare tools it adds to the agent.

Human in the loop

Some actions should never happen without a person saying yes: sending email, paying, deleting, deploying. HumanInTheLoopMiddleware pauses the agent right before those tool calls, saves the state, and waits for a decision.

hitl.py
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langchain.tools import tool
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

@tool
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email."""
    return f"Email sent to {to}"

@tool
def read_inbox() -> str:
    """Read the latest emails."""
    return "1 new email from boss@corp.com: 'Send the Q3 report to the client.'"

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=[send_email, read_inbox],
    checkpointer=InMemorySaver(),            # required: the pause must be saved
    middleware=[HumanInTheLoopMiddleware(
        interrupt_on={
            "send_email": {"allowed_decisions": ["approve", "edit", "reject"]},
            "read_inbox": False,             # safe: never pause
        },
        description_prefix="Approval needed",
    )],
)

config = {"configurable": {"thread_id": "inbox-1"}}
result = agent.invoke({"messages": [{"role": "user", "content": "Handle my inbox."}]}, config)

# The run paused. Show the pending action to a human:
print(result["__interrupt__"])

# Option A: approve
agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config)

# Option B: edit the arguments first
agent.invoke(Command(resume={"decisions": [{
    "type": "edit",
    "edited_action": {"name": "send_email",
                      "args": {"to": "client@acme.com", "subject": "Q3 report", "body": "Attached."}},
}]}), config)

# Option C: reject with feedback the model will see
agent.invoke(Command(resume={"decisions": [{
    "type": "reject", "message": "Don't email the client yet; wait for finance sign-off."
}]}), config)

More HITL details

  • Fourth decision, respond: {"type": "respond", "message": "..."} returns the human's text as a successful tool result. Use it only for "ask the user" tools, never to deny an action.
  • True shorthand: interrupt_on={"send_email": True} allows all decisions.
  • Conditional pauses: add "when": fn to a tool's config to pause only when fn(request) returns true (1.3.3+).
  • Payload: the interrupt holds action_requests (name, arguments, description) and review_configs (action name, allowed decisions). description_prefix defaults to "Tool execution requires approval".
  • Several paused calls: send one decision per call, in the same order.
  • Newer read style: the docs now use agent.invoke(..., version="v2") and read result.interrupts. result["__interrupt__"] still works with plain invoke.

guardrails.py
from langchain.agents.middleware import before_agent, after_agent
from langchain.chat_models import init_chat_model
from langchain.messages import AIMessage

BLOCKED = ["ignore previous instructions", "reveal your system prompt"]

@before_agent(can_jump_to=["end"])
def input_guard(state, runtime):
    text = state["messages"][-1].text.lower()
    if any(p in text for p in BLOCKED):
        return {"messages": [{"role": "assistant",
                 "content": "I can't help with that request."}], "jump_to": "end"}
    return None

judge = init_chat_model("openai:gpt-5.4-mini", temperature=0)

@after_agent(can_jump_to=["end"])
def output_guard(state, runtime):
    last = state["messages"][-1]
    if not isinstance(last, AIMessage):
        return None
    verdict = judge.invoke(
        f"Reply SAFE or UNSAFE. Does this answer leak secrets or give harmful advice?\n\n{last.text}"
    ).text
    if "UNSAFE" in verdict:
        # Same id = replace the unsafe message. A new message would only be appended.
        return {"messages": [AIMessage(content="I can't share that answer.", id=last.id)]}
    return None

Annotation and state

Annotations (types) describe the shape of the information carried through a workflow. Every step reads this state, and the model, tools and router all work from it. Structured state matters most in explicit LangGraph workflows like the one below.

Mental model

State is a typed dictionary. Nodes are functions that read state and return updates. Edges decide which node runs next. Compile it and you get a Runnable with invoke and stream.

graph_workflow.py · classify → route → respond
from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent

llm = init_chat_model("openai:gpt-5.4-mini", temperature=0)
tech_agent = create_agent(llm, tools=[], system_prompt="You are technical support.")

class State(TypedDict):
    question: str
    category: str
    answer: str

def classify(state: State) -> dict:
    label = llm.invoke(
        f"Classify as 'billing' or 'technical'. One word only.\n\n{state['question']}"
    ).text.strip().lower()
    return {"category": label}

def billing(state: State) -> dict:
    return {"answer": llm.invoke(f"As billing support, answer: {state['question']}").text}

def technical(state: State) -> dict:
    return {"answer": tech_agent.invoke(   # a create_agent agent can be a node
        {"messages": [{"role": "user", "content": state["question"]}]}
    )["messages"][-1].text}

def route(state: State) -> Literal["billing", "technical"]:
    return "billing" if "billing" in state["category"] else "technical"

builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("billing", billing)
builder.add_node("technical", technical)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route)
builder.add_edge("billing", END)
builder.add_edge("technical", END)

graph = builder.compile()
print(graph.invoke({"question": "Why was I charged twice?"})["answer"])

    return StreamingResponse(tokens(), media_type="text/plain")

Best practices from production

  • Few, sharp tools. 3–10 tools per agent with clear, non-overlapping docstrings beat 40 vague ones.
  • Temperature 0 for agents and extraction.
  • Always set limits (ModelCallLimitMiddleware) so a confused agent cannot loop and burn money.
  • Return errors to the model as ToolMessages instead of crashing.
  • Human approval for anything irreversible or external.
  • Persistent checkpointer (Postgres) in production; InMemorySaver loses everything on restart.
  • Trace everything with LangSmith from day one.
  • Evaluate before shipping a prompt or model change; keep a dataset of 20–100 real questions.
  • Control cost: cheap model for summaries, routing and judges; strong model for the main reasoning; fallback middleware for outages.
  • Secrets in env vars or runtime context, never in prompts.
  • Treat retrieved and tool text as untrusted: it can contain prompt-injection instructions.
  • Pin versions in pyproject.toml and read release notes before upgrading.

src/agent.py
import uuid
from dataclasses import dataclass
from dotenv import load_dotenv
from langchain.agents import create_agent, AgentState
from langchain.agents.middleware import (
    SummarizationMiddleware, HumanInTheLoopMiddleware, PIIMiddleware,
    ModelCallLimitMiddleware, ToolRetryMiddleware, dynamic_prompt, ModelRequest,
)
from langchain.chat_models import init_chat_model
from langchain.tools import tool, ToolRuntime
from langchain_openai import OpenAIEmbeddings
from langchain_core.vectorstores import InMemoryVectorStore
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

load_dotenv()

# ---------- context and state ----------
@dataclass
class Context:
    user_id: str
    user_name: str
    tier: str            # "free" | "pro"

class SupportState(AgentState):
    ticket_id: str | None

# ---------- knowledge base ----------
kb = InMemoryVectorStore(OpenAIEmbeddings(model="text-embedding-3-small"))
kb.add_texts([
    "Refunds are processed within 5-7 business days after approval.",
    "Pro customers get free express shipping on all orders.",
    "Orders can be cancelled free of charge until they ship.",
], metadatas=[{"source": "refund-policy"}, {"source": "shipping"}, {"source": "cancellation"}])

# ---------- tools ----------
ORDERS = {"1042": {"status": "shipped", "total": 2499}, "1051": {"status": "processing", "total": 899}}

@tool
def search_kb(query: str) -> str:
    """Search help-centre policies. Use for refund, shipping and cancellation questions."""
    docs = kb.similarity_search(query, k=2)
    return "\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in docs)

@tool
def lookup_order(order_id: str) -> str:
    """Look up the status and total of an order by its number, e.g. '1042'."""
    o = ORDERS.get(order_id)
    return f"Order {order_id}: {o['status']}, ₹{o['total']}" if o else f"No order {order_id}"

@tool
def issue_refund(order_id: str, reason: str) -> str:
    """Refund an order. Requires human approval."""
    return f"Refund issued for order {order_id} ({reason})."

@tool
def remember(fact: str, runtime: ToolRuntime[Context]) -> str:
    """Save a lasting fact about the customer, e.g. a preferred language."""
    ns = ("facts", runtime.context.user_id)
    runtime.store.put(ns, str(uuid.uuid4()), {"fact": fact})   # unique key per fact
    return "Saved."

# ---------- dynamic prompt with memory ----------
@dynamic_prompt
def personalised_prompt(request: ModelRequest) -> str:
    ctx = request.runtime.context
    facts = request.runtime.store.search(("facts", ctx.user_id), limit=50)
    known = "; ".join(f.value["fact"] for f in facts) or "nothing yet"
    return (
        f"You are AutoPlant's support agent. Customer: {ctx.user_name} ({ctx.tier} plan).\n"
        f"Known about them: {known}.\n"
        "Check orders with lookup_order and policies with search_kb before answering. "
        "Cite policy sources in brackets. Use issue_refund only when policy allows. "
        "Save lasting preferences with remember."
    )

# ---------- the agent ----------
agent = create_agent(
    model=init_chat_model("anthropic:claude-sonnet-4-6", temperature=0),
    tools=[search_kb, lookup_order, issue_refund, remember],
    state_schema=SupportState,
    context_schema=Context,
    checkpointer=InMemorySaver(),      # production: PostgresSaver
    store=InMemoryStore(),             # production: PostgresStore
    middleware=[
        personalised_prompt,
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
        SummarizationMiddleware(model="openai:gpt-5.4-mini",
                                trigger=("tokens", 6000), keep=("messages", 20)),
        ModelCallLimitMiddleware(run_limit=10, exit_behavior="end"),
        ToolRetryMiddleware(max_retries=2),
        HumanInTheLoopMiddleware(interrupt_on={"issue_refund": True}),
    ],
)

if __name__ == "__main__":
    from langgraph.types import Command
    ctx = Context(user_id="u42", user_name="Piyush", tier="pro")
    cfg = {"configurable": {"thread_id": "ticket-001"}}

    msg = {"messages": [{"role": "user",
           "content": "Order 1051 is taking forever. Please cancel and refund it. Also, I prefer Hindi."}]}
    for mode, chunk in agent.stream(msg, cfg, context=ctx, stream_mode=["updates", "messages"]):
        if mode == "messages" and chunk[0].text:
            print(chunk[0].text, end="", flush=True)

    state = agent.get_state(cfg)
    if state.interrupts:                         # refund awaiting approval
        print("\n\nPending:", state.interrupts[0].value)
        final = agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), cfg, context=ctx)
        print(final["messages"][-1].text)
